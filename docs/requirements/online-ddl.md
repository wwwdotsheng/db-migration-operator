# 在线 DDL

目标：对明确支持的表重建操作，把数据复制和增量同步放在后台执行，让业务继续读写原表；将需要阻塞业务的时间限制在可控的切表窗口。影子库预演仍负责验证结构和 SQL，不能作为在线能力的验收依据。

## 开题报告表述

**（7）在线变更执行。** 系统通过统一的 Driver 接口支持 MySQL 和 PostgreSQL，并按数据库类型和变更操作接入相应的执行策略。首版以 MySQL 单表重建为验证场景，例如将非键列的数据类型从 `INT` 扩大为 `BIGINT`。结构预演通过后，控制器调用 MySQL 在线执行策略进行预检。该策略确认二进制日志采用 ROW 格式，能为 `gh-ost` 提供增量同步所需的行变更事件，同时检查变更前后的表是否保留共同的主键或合格的唯一键，以及目标表是否存在执行器不支持的外键或触发器。预检未通过时，控制器记录具体原因并停止本次在线任务。

预检通过后，控制器创建在线执行 Job，由 `gh-ost` 建立迁移副本、分批复制数据并同步增量写入。复制和同步期间，原表继续提供读写服务；待增量追平后再尝试原子切表，以缩短业务写入受阻的时间。控制器跟踪任务阶段并更新迁移状态，在确认切换结果和目标表结构符合预期后，将迁移账本标记为完成。执行策略通过接口接入，PostgreSQL 可在后续接入并发创建索引等原生低阻塞策略。

## 首版范围

- 先支持 MySQL 8.0 InnoDB 的单表、单条 ALTER，使用独立执行 Job 调用 gh-ost。验收用例为将有主键的业务表中的非键列从 INT 扩大为 BIGINT。原生 ALTER 对这种类型变更需要重建表，且不允许并发写入。
- 控制器调用 MySQL 在线执行策略进行预检。该策略检查执行器读取的 binlog、变更前后共用的迁移键以及外键和触发器等限制。预检失败时，控制器报告具体原因，不回退到直接执行 ALTER。
- 在线执行方式独立于 changeType。Expand、Contract、Mixed 继续描述变更意图。PostgreSQL 和多表迁移的在线执行不在首版范围。

## 执行与恢复

1. 影子预演通过后，按照现有迁移身份和账本规则登记执行，再启动或认领对应的在线执行 Job。控制器重启后先认领已有 Job；同一迁移不能同时启动两个执行器，同一目标库的其他迁移在此期间继续等待。
2. Job 创建目标库内的迁移副本、分批复制数据并追平增量写入。复制期间允许限速，原表继续承载读写。追平后，Job 在允许的时机尝试原子切换。
3. 切换的锁等待应有超时和有限重试。拿不到锁时，及时终止本次尝试并释放等待，保持原表继续服务。长事务导致的锁排队也计入业务阻塞时间。
4. 确认已切换且新表结构符合预期后才写入账本 Done。Job 失联或切换结果不确定时，进入 MigrationRecoveryRequired，保留诊断信息，禁止盲目重跑。

## 验收

在相同初始数据、并发读写负载和数据库资源下，对比原生 ALTER 与在线执行。数据量应足以让原生操作出现可观测的写阻塞。分别记录总迁移时间、复制阶段的读写吞吐与 p95/p99 延迟、切换阶段最长连续写阻塞，以及请求错误和超时数。首版实验可将最长连续写阻塞不超过 2 秒作为候选目标，正式实验前固定负载、阈值与测量方法。

同时验证三件事：迁移后结构符合预期且并发写入未丢失；长事务阻挡切表时，超时退出后原表仍可用；控制器在复制或切换期间重启，不会重复启动执行器或对未确认的结果记 Done。
