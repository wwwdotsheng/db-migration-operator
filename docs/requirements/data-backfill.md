# 数据回填首版设计

目标：在单实例 MySQL 上对同一张表的历史记录补齐新字段。控制器负责前置版本、任务启动、进度和完成判断；回填 Job 按主键分批执行。首版只支持一种可重复执行的规则：从同一行的现有列复制到尚为空的目标列。用已有结构化省份编码验证，不解析自由文本地址。

## 任务契约

- 将加列、回填和依赖回填完成的后续 DDL 拆成不同迁移版本。回填使用结构化配置声明表、单列正整数主键、源列、目标列和批大小，不与任意 SQL 混在同一任务中。字段名和数据类型在执行前核验；首版要求源列与目标列类型兼容，目标列可空。
- 目标表和进度表都使用 InnoDB。主键在扫描期间不可变，不复用已经扫描过的主键。
- 开始前由调用方确认所有业务写入入口已能在同一次数据库更新中维护源列与目标列，或者相关写入已暂停。控制器不从 Kubernetes 部署状态推断双写是否正确。双写启用时，源值变为 NULL 也要同步到目标列。
- 任务开始时持久化历史主键上界和内容校验和。上界以外的新记录由应用兼容写入负责。回填只填目标为空、源值可用的行，不覆盖已经写入的目标值。

## 批次与恢复

1. 控制器检查前置版本、表结构和回填配置，登记本次迁移并创建或认领同一身份的执行 Job。对同一目标库，回填执行期间继续阻止其他迁移推进。
2. Job 按主键顺序选择下一批实际存在的行。批大小限制每批扫描的主键数量，不假设主键连续。更新在数据库内读取当前源值，如 `SET province_code = shipping_province_code`，并用 `province_code IS NULL` 保护业务已写入的值。
3. 每批在一个短事务内锁定进度记录、更新业务行并推进检查点。检查点记录已扫描到的主键和累计更新数，即使这一批更新了零行，也按扫描范围正常前进。控制器重启或提交结果未收到时，重新读数据库检查点；已经提交的批次不会再从头扫，未提交的批次可以安全重试。锁等待或死锁时回滚整个批次，并进行有限重试。
4. 扫完历史范围后，分批核验源列与目标列是否一致，记录未填和不一致的行数。首版源为 NULL 时允许目标同为 NULL；不将空值写成假的业务值。校验有异常时阻塞后续版本，提供核对线索；校验通过才写账本 Done。

现有账本把未确认的 Applying 当成待人工核对。接入回填时，要为这类有事务检查点的任务增加识别与续跑路径。普通 DDL 仍采用原有的保守恢复规则。

## 最小验收

1. 用一张无外键的 MySQL 业务表准备历史数据，分别提交加列、回填和建索引任务；确认回填验收通过前，建索引任务一直等待。
2. 回填期间持续新增业务数据，并对已回填和未回填的行改源值；验证应用同步写入的目标值不被覆盖，结束时历史范围内两列一致。再故意制造一个不一致值，确认校验失败时账本不会标记 Done。
3. 分别在批次提交前、提交后但 Job 尚未报告进度时中断执行器。恢复后核对数据和数据库检查点，确认未跳过历史记录、未丢失并发写入，也未重复执行已提交的批次。
4. 观察批次耗时、累计扫描与更新行数，以及业务请求的延迟和超时。先用固定批大小验证正确性，再根据延迟调整批大小和批次间隔。
